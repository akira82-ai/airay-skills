## Default Behavior

**🔥 最高铁律：前两步是命根。**

这个技能质量的天花板，完全由前两步决定：

1. **阶段 1 — 确定目标用户**：没有确认受众，后面的 100 问就是无的放矢，不准跳过。
2. **阶段 2 — 搜集整理资料，拿到信源的原始内容存入本地**：不是收集标题、不是收集链接列表、不是凭印象写——而是**真正把每个命中信源的原始正文抓回来、原汁原味落到本地文件**。

前两步没做扎实，后面六章建模和 100 问全是空中楼阁。宁可在这两步多花时间、多追问、多抓几个源，也不要带着空洞的资料直接往后冲。缺资料时先追问收窄，绝不拿空主题硬凑。

其他默认行为：

- 默认中文输出，除非用户明确要求其他语言。
- 默认面向技术、产品、工具、方法论、工程实践类主题。
- 默认串行执行：受众确认 → 搜索引擎广度 → 站点深挖 → 资料落盘 → 六章建模 → 100 问。
- 每一步执行完都要展示结果，等用户看到后再进入下一步，不要一口气并行跑完。
- 默认先建立"读者画像卡"，再决定后面的 100 问重心。
- 如果用户明确说"一次性输出""直接给完整 100 问""不用等我确认"，才跳过中间确认。
- 默认最终结果只输出 100 问清单，不附来源、不扩成文章、不补写长解释。
- 缺资料时先追问，不要拿空主题硬凑 100 个泛问题。
- 问题质量取决于真实资料和真实搜索，不要编造社区踩坑、版本更新或用户反馈。

## 职责边界

本技能只负责把一个主题拆成高质量的 100 个问题。

不要做这些事：

- 不负责把问题扩写成文章。
- 不负责把问题改写成短视频脚本、课程大纲或销售文案。
- 不输出"参考资料摘要"或"资料综述"替代问题清单。
- 不为了凑数写说明书式问题、定义式标题或关键词堆砌标题。
- **资料收集阶段绝对不写答案**。搜索是为了找"哪些问题值得问"，不是为了做摘要、写解释或输出答案。任何搜索结果只能提炼成"问题候选点"，不能提炼成"知识点说明"。

## 读者画像卡

在生成 100 问之前，先建立这张卡：

- 这 100 问写给谁
- 这群人正卡在哪
- 他们最怕踩什么坑
- 他们最想拿走什么结果
- 他们会因为什么问题愿意点开或保存

先从用户输入和资料里推断；不够时再从搜索结果里补；只有缺口仍然很大时，才追问用户 1-2 个关键问题。

## 工作流

整体严格串行，分三大阶段：受众确认 → 资料收集（两步串行）→ 问题提炼生成。每一步执行完都要把结果展示给用户，不要并行抢跑。

### 阶段 1：确定受众（命根之一，必须和用户确认）

先和用户确认读者画像，确认后才进入搜索。这一步不能跳过——没有确认受众，后面 100 问就是无的放矢。

确认清单：

- 主题名称
- 这 100 问写给谁（角色、水平、场景）
- 这群人正卡在哪
- 他们最怕踩什么坑
- 他们最想拿走什么结果
- 用户已有的参考链接、文档、踩坑经验（如果有）

执行方式：

1. 先从用户输入里提取已明确的项。
2. 缺失项一次性追问，最多 1-2 个关键问题，不要逐条审问。
3. 把推断出的读者画像卡完整展示给用户确认。
4. 用户点头后才进入阶段 2。

阶段 1 的输出格式：

```markdown
## 读者画像卡（待确认）

- 主题：{主题}
- 读者：{角色 + 水平 + 场景}
- 卡点：{当前最卡的环节}
- 怕的坑：{最怕踩的代价}
- 想要的结果：{最想拿走的东西}
- 已有资料：{链接/经验/对比，或"无"}

确认无误后我开始按顺序搜索。
```

### 阶段 2：资料收集——拿到信源原始内容并落盘（严格串行，两步）

这一阶段是整个技能执行最容易出现"乱跑"的地方，也是**这个技能的命根**。必须严格按下面两个子步骤**串行**执行，每一步跑完展示结果，再进入下一步。不要并行。

阶段 2 的唯一目标：**把命中信源的原始正文真正抓回来，原汁原味落到本地文件**。不是收集链接、不是收集标题、不是记几个"候选页面"，而是实打实地拿到每一个信源的原始内容存进本地。链接和标题只是过程，本地里的原文才是结果。

> ⚠️ **严禁使用搜狗（sogou）**。本技能整个资料收集阶段不得调用、模拟或建议搜狗/搜狗微信搜索（`sogou.com`、`weixin.sogou.com`），也不得为搜狗生成关键词。任何"搜狗关键词""搜狗微信搜索"的环节都已删除。

#### 步骤 2.1：搜索引擎广度搜索（Bing / Google）

定位：用智能生成的中英文关键字做第一轮广度搜索，发现候选页面。

智能关键字生成规则：

| 维度 | 做法 |
|---|---|
| 双语 | 每个搜索方向同时生成中文 + 英文关键字，不能只用一种 |
| 变形 | 原词、同义词、行业黑话、缩写、产品代号都要覆盖（如"降级"→degrade/fallback/circuit break） |
| 组合 | 主题词 × 痛点词 × 场景词（如 "X + 踩坑/production failure/real world"） |
| 年份 | 所有关键字强制带当前年份 |
| 分型 | 概念类、踩坑类、对比类、版本类各自出不同关键字组合 |

默认搜索框架（4 个方向）：

1. 概念与定位：是什么、为什么重要、和谁容易混淆。
2. 踩坑与反模式：踩坑、常见错误、不要做什么、社区吐槽。
3. 进阶与争议：最佳实践、高级用法、争议点、什么时候过时。
4. 产品专属：新功能、修复项、废弃项、迁移路径。

执行要求：

- 逐个方向搜索，**不要一次性并行所有方向**。每个方向搜完展示结果，再搜下一个。
- 每个方向至少跑 1 个中文 + 1 个英文查询。
- 产品类主题必须额外搜 `release notes` 或 `changelog`。
- 所有搜索词带当前年份。
- 遇到登录墙、反爬或正文残缺，直接换源，不硬抓。
- 搜索结果只记录"候选页面 + 一句话定位"，**不做摘要、不写答案**。

步骤 2.1 完成后输出：

```markdown
## 步骤 2.1 结果：搜索引擎广度搜索

### 方向 1：概念与定位
- 关键字：`{中文关键字}` / `{english keywords}`
- 候选页面：
  - {页面标题} — {一句话定位，如"官方概念说明"/"社区对比帖"}
  - ...

### 方向 2：踩坑与反模式
...

进入步骤 2.2：站点深挖。
```

#### 步骤 2.2：指定站点深挖（site: 限定搜索）

定位：等步骤 2.1 全部跑完后，针对高价值站点用 `site:` 限定做第二轮深挖，把流量导向真实经验、社区讨论和一手源。

默认站点池：

- 官方：`site:github.com`（仓库、releases、issues、discussions）
- 社区：`site:reddit.com`、`site:news.ycombinator.com`
- 问答：`site:stackoverflow.com`
- 长文经验：`site:medium.com`、`site:substack.com`
- 中文补充：`site:v2ex.com`、`site:sspai.com`

执行要求：

- 根据步骤 2.1 的结果，挑出 3-5 个最值得深挖的站点。
- 每个站点逐个搜，**不要并行**。每个站点搜完展示结果，再搜下一个。
- 每个站点至少跑 1 个查询，关键字复用步骤 2.1 的智能关键字，但加上 `site:` 限定。
- 这一步的目标是把广度搜索发现的"候选页面"升级成"可提炼问题的真实素材"。
- 仍然**不做摘要、不写答案**，只记录"页面 + 定位 + 可提炼的问题方向"。

步骤 2.2 完成后输出：

```markdown
## 步骤 2.2 结果：站点深挖

### site:reddit.com
- 关键字：`site:reddit.com {关键字}`
- 命中：
  - {帖子标题} — {定位，如"真实踩坑复盘"/"迁移争议讨论"}
  - ...

### site:v2ex.com
...

进入步骤 2.3：资料落盘。
```

#### 步骤 2.3：资料落盘

定位：前两步跑完后，把命中页面的**原始正文**抓回来，原汁原味存进本地文件，为后面六章建模和 100 问生成留底。

**资料落盘规则（核心：原汁原味，一份资料一个文件，禁止二次加工）：**

- 用 web 抓取工具把每个命中页面的正文整页抓回，**原文照搬**存入本地 Markdown 文件，**一份资料一个文件**——一个 URL 就存为一个独立 `.md` 文件，不要把多个页面的内容拼进同一个文件。
- **严禁对抓回来的内容做任何二次加工**：不摘要、不改写、不缩写、不提炼、不翻译、不润色、不写"一句话定位"、不做"问题方向"标注。网页写的是什么，文件里就是什么。
- 原文之外的元信息只保留三项：页面标题、URL、抓取日期。其余一律不许加。
- 正文抓不全（登录墙、反爬、JS 渲染拿不到）的页面，记下 URL 和"正文缺失原因"，**不要凭印象补写**。
- 目录：**必须先问用户**，由用户提供资料落盘的存储路径。用户给出路径前不要动手抓取，也不要替用户预设默认路径。拿到路径后，目录不存在就新建。
- 文件命名：`{序号3位}_{页面标题slug}.md`，如 `001_xxx-踩坑复盘.md`、`002_yyy-best-practices.md`。
- 每个文件内部结构：`# {页面标题}` → `> 来源：{URL}` → `> 抓取：{日期}` → 原文正文。

步骤 2.3 完成后输出：

```markdown
## 步骤 2.3 结果：资料落盘

### 资料已落盘（原汁原味，未加工，一页一文件）
- 目录：`{用户提供的路径}`
- 共抓取 {N} 个页面原文 → {N} 个 .md 文件
- 正文缺失页面：{M} 个（已记 URL + 缺失原因，未补写）

资料收集阶段完成。进入阶段 3：六章建模 + 100 问生成。
```

### 阶段 3：六章建模

把用户资料和搜索结果压成 6 个章节，形成"认知递进 + 实战纵深 + 哲学收束"。

默认结构：

1. 基础认知与定位
2. 核心架构与关键机制
3. 踩坑与反模式
4. 验证、质量与进阶技巧
5. 工程落地与场景实战
6. 边界、替代与反思

默认先给出 6 章名称和每章定位；用户无异议再进入 100 问生成。只有在一次性输出模式下，才直接跳过确认。

### 阶段 4：按章生成 100 问

严格按六章生成，总数控制在 100 问，章节数量允许小幅浮动：

- 第一章约 15 问
- 第二章约 20 问
- 第三章约 15 问
- 第四章约 20 问
- 第五章约 15 问
- 第六章约 15 问

第三章必须是最有经验感的一章。这里的问题要尽量像从群聊、issue 区、踩坑帖里直接提炼出来，而不是文档换皮。

问题数量优先服从读者关心度，而不是平均对称。用户最关心的 1-2 章可以明显多给，低关心度章节可以少给，只要总数仍控制在 100 问附近即可。

问题风格不要只有一种味道。默认按这三类混合：

- 传播型问题：优先制造点击、讨论、转发欲，强调冲突、反直觉、代价、误判。
- 收藏型问题：优先制造保存、回查价值，强调场景、判断、排错、决策。
- 认知型问题：优先搭建判断框架，强调边界、前提、适用条件、替代关系。

默认比例：

- 传播型约 30%
- 收藏型约 50%
- 认知型约 20%

整体以收藏型为主，传播型负责拉点击，认知型负责托住框架。不要把 100 问写成 100 个同味道的标题。

### 阶段 5：问题写作铁律

每条问题都要通过这组规则：

1. 以疑问词开头，如“为什么”“怎么”“如何”“是不是”“到底”。
2. 不写陈述句，不写“X 的定义”“X 的优势有哪些”。
3. 一条只打一个点，不塞两个问题。
4. 长度尽量控制在 15-30 个汉字。
5. 不用破折号和冒号在题目内部补解释。
6. 经验优先，不要说明书口吻。
7. 问题要够细，能落到具体动作、具体场景、具体翻车点。
8. 优先保留冲突感、反直觉和代价感。
9. 如果一个问题很容易用“是/否”回答，重写。
10. 同一个角度不要换皮重复。
11. 每个好问题背后都要隐含一个读者代价，如时间、返工、误判、成本、机会损失。
12. 删除那些“答了也不会改变行动”的无感问题。
13. 先写“和我有关”，再写“这个主题本身”。
14. 先写“错误代价”和“决策后果”，再写中性知识。
15. 先写场景与判断，再写概念与定义。

重点改写方向：

- 少写“怎么使用 X”
- 多写“为什么用了 X 反而出问题”
- 少写“X 有什么价值”
- 多写“什么时候继续用 X 其实已经错了”

风格提醒：

- 传播型问题要让人想点开、转发、讨论。
- 收藏型问题要让人觉得“以后一定会用到，先存下来”。
- 认知型问题要帮助读者建立判断，不要退化成百科解释。
- 定义题、说明书题、百科题严格限量，只能作为框架补位，不能成为主流。

### 阶段 6：全量质检

输出前逐项检查：

- 是否严格是 6 章结构
- 是否总数接近 100 问
- 是否残留陈述句标题
- 是否残留破折号、冒号解释
- 第三章是否真的更像踩坑而不是说明书
- 产品类主题是否真的利用了 release notes / changelog 信息
- 是否明确围绕读者画像卡，而不是围绕作者自嗨
- 是否删掉了“答了也没行动变化”的无感问题
- 是否同时包含传播型、收藏型、认知型，而不是单一风格刷满
- 是否以收藏型为主，而不是全部在喊口号
- 最终结果是否只包含问题清单，没有多余解释

如果任一项不达标，先重写再输出。

## 产品类主题的硬规则

如果主题是产品、工具或服务，必须额外检查：

- 今年的 release notes
- 今年的 changelog
- 今年关于更新、新功能、修复项、弃用项的讨论

这些信息要这样转成问题：

- 新功能：是不是你的场景的实际解法
- 修复项：这个坑你中过吗，为什么当时难排查
- 弃用项：为什么还在用旧路径的人该尽快迁移

如果没有做这一步，不要假装已经完成产品类主题的 100 问。

## 输出格式

最终只输出 Markdown 清单，使用这个骨架：

```markdown
# 《{主题名称} · 100 问》

## 一、{第一章名称}
1. ...

## 二、{第二章名称}
...
```

默认不要额外输出：

- 来源列表
- 写作说明
- 章节点评
- 后续文章建议
- “我参考了什么资料”之类的补充

## 一次性输出模式

当用户明确要求“一次性输出”时：

- 不等待章节确认
- 直接完成资料缺口的最小追问或合理假设
- **但前两步的硬要求不变**：受众仍要确认（可一次问清），信源原始内容仍必须真正抓回本地，不许因为"一次性"就跳过抓取、只凭假设往下写。
- 在内部完成搜索、建模、质检
- 最终仍然只输出 100 问清单

## 失败条件

出现以下情况时，不要直接生成终稿：

- 连主题都不明确
- 用户要求的是文章，而不是问题清单
- **没有拿到信源的原始内容落到本地**——只有链接列表或标题、没有真实抓回来的正文，就不许进入建模阶段。先补抓，补不到就追问收窄。
