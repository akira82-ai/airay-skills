# Prompt Diagnosis Checklist

## Six Checks

| 项目 | 好的表现 | 常见问题 |
|---|---|---|
| 任务目标 | 能判断输出是否达成目的 | 只说“帮我写/优化/总结” |
| 背景条件 | 提供必要业务事实和限制 | 模型需要猜场景 |
| 输出格式 | 有固定结构、字段或模板 | 只说“清晰一点” |
| 边界禁令 | 明确不能做什么 | 容易推测、夸大、越权 |
| 验收标准 | 可观察、可判断 | 满意度全靠主观感觉 |
| 冲突验证 | 有优先级和证据要求 | 要求互相打架或不可验证 |

## Scoring

- 90-100：结构完整，可直接使用，只需轻微润色。
- 80-89：目标和格式明确，但背景、边界或验收不足。
- 70-79：能看出任务，但模型仍需大量猜测。
- 60-69：只有粗略意图，必须补场景后再改写。
- 60 以下：先追问，不直接生成完整提示词。

评分不用每次展示。用户要求评估或诊断时再展示。

## Ask Or Rewrite

直接改写：

- 用户给了原始提示词和大致使用场景。
- 缺失信息可以用变量占位。
- 风险不高，输出不涉及合规、法律、医疗、金融决策。

先追问：

- 完全不知道任务用途。
- 输出对象会显著影响语气和格式。
- 用户要求对外发布、客户沟通、管理层决策或合规内容。
- 原提示词包含敏感数据、安全边界或不可确认事实。

## Diagnosis Language

诊断要具体：

- 不说：“提示词不够清晰。”
- 要说：“缺少受众和验收标准，模型不知道该面向新人解释，还是给管理层做决策摘要。”

- 不说：“需要更多上下文。”
- 要说：“缺少业务场景、输入材料来源和禁止推测要求，容易生成看似合理但不可验证的结论。”

## Minimum Optimized Prompt Structure

```text
你要完成的任务：

背景与输入：

输出要求：

限制要求：

验收标准：
```
