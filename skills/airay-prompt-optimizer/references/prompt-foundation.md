# Prompt Foundation

来自 lesson2：基础提示词及其应用。

## Core Principle

提示词不是灵感句子，而是任务规格说明。优化时先把用户脑中的预期显式化为模型可执行的约束集合。

## Diagnosis Points

检查原始提示词是否包含：

- 任务目标：要完成什么，为什么做，什么结果算有用。
- 受众对象：输出给谁看，读者背景、权限和关注点是什么。
- 背景条件：业务场景、已有材料、时间窗口、资源限制、历史决策。
- 输出结构：标题层级、段落顺序、表格字段、JSON 键名、长度。
- 边界禁令：不能推测、不能夸大、不能泄露、不能改变事实。
- 验收标准：必须包含哪些模块，每个模块回答什么问题，如何判断合格。

## Rewrite Rules

- 先写任务目标、受众和边界，再写输出形式。
- 把“更好一些”“专业一点”改成可判断要求。
- 背景只保留与任务成败相关的信息，避免堆无关材料。
- 格式写成明确模板，不写“尽量清晰”。
- 对外、管理层、合规相关内容必须写负向约束。
- 重复高优先级约束：开头一次、执行检查一次、结尾一次即可。

## System And User Layers

把长期规则和当前任务分开：

- 系统层：输出语言、合规边界、风格底线、事实要求。
- 用户层：当前任务目标、输入材料、具体输出格式。

如果用户要求构建可复用提示词模板，优先把稳定规则放在系统层，把可替换内容放在用户层变量。

## Conflict Priority

复杂提示词经常出现互斥要求。改写时显式声明优先级，例如：

```text
优先级：事实准确 > 合规边界 > 输出格式 > 风格优化。
如果无法同时满足，请优先保证高优先级要求，并说明取舍原因。
```

常见冲突：

- 字数很短，但要求信息完整。
- 风格要活泼，但内容面向正式对外沟通。
- 要快速给结论，但事实来源不足。
- 要格式固定，但输入材料结构混乱。

## Common Fixes

- 目标不清：补“用于什么决策/行动/沟通”。
- 背景不足：补业务场景、对象、约束、已有材料。
- 输出漂移：补固定结构和字段。
- 结果空泛：补验收标准和示例粒度。
- 风险过高：补事实边界、禁用项和优先级。
